## 1. เป้าหมายและขอบเขต

สร้าง framework สำหรับ NPC คู่คิดและคู่ร่วมมือในเกม Unity โดยพิสูจน์ผ่าน Room01 ว่าผู้เล่นรู้สึกว่ามีเพื่อนช่วยสังเกต แลกเปลี่ยนหลักฐาน และร่วมลงมือหาทางออก ความสัมพันธ์ส่งผลต่อความร่วมมือและระดับคำใบ้ ขณะที่ NPC ยึดข้อเท็จจริงของเกมเสมอ

เป้าหมายการนำไปใช้ต่อรอบแรกคือเกม Unity 2D แนวสำรวจ ผจญภัย ปริศนา และ visual novel ที่ใช้การคุย ความทรงจำ ความสัมพันธ์ และกิจกรรมร่วมมือคล้ายกัน ยังไม่รับรองการย้ายข้าม engine หรือกลไกทุกแนวโดยไม่เขียนโค้ด

ผลส่งมอบหลัก:

1. Room01 ที่มีเหตุการณ์ร่วมแก้ปริศนาจบได้ในเดโมเป้าหมาย 5–8 นาที
2. ขอบเขต Core / ข้อมูลเกม / ตัวเชื่อมเกมที่ชัด และรักษาพฤติกรรมเดิมได้
3. ตัวอย่างต่างธีมใน Unity project ใหม่ พร้อมคู่มือติดตั้งและข้อจำกัดที่พิสูจน์แล้ว
4. หลักฐานทดสอบแยก automated, simulated AI, manual playtest และ real provider อย่างตรงไปตรงมา

## 3. กติกาที่ต้องรักษา

- GameState หรือ host-game state ที่เชื่อมเข้ามาเป็นผู้ตัดสินความจริงและผลของ action
- AI เสนอเจตนาและแต่งสำนวนได้ แต่ไม่ให้รางวัล เปลี่ยนสถานะ สร้างหลักฐาน หรือข้ามเงื่อนไขเอง
- ข้อมูลที่ NPC ไม่รู้และคำตอบที่ยังไม่อนุญาตต้องไม่หลุดในคำพูด ความทรงจำ หรือข้อความล้อมคำใบ้
- คำขอร่วมมือมาจากผู้เล่นพูด/พิมพ์เอง ไม่มีปุ่มเลือกคำสั่งแทนการสนทนา
- คำสั่งกำกวมให้ถามกลับในบทสนทนา เมื่อเป้าหมายไม่ชัดห้ามเดาแล้วลงมือ
- NPC ชวนคุยผ่านสัญญาณที่ผู้เล่นเลือกเข้าไปคุยได้ ไม่เปิดกล่องกลางจอรบกวนตลอดเวลา
- ความสัมพันธ์ต่ำยังเล่นจบได้ คำใบ้มากขึ้นไม่เท่ากับเปิดเฉลยอัตโนมัติ
- เมื่อ API ล้มเหลว/ช้า/ถูกยกเลิก เกมเล่นต่อได้และออกจากบทสนทนาได้
- ผลตอบกลับเก่าห้ามเริ่ม action หลังยกเลิก เปลี่ยนฉาก หรือเปลี่ยนคำสั่งแล้ว
- ยังไม่ใช้ key จริงหรือโควตาจริง ใช้ simulated provider ก่อน; รายงาน real-provider test ว่ายังไม่ทำ
- การ push, เปิด PR, ส่ง comment หรือ merge ให้ทำเมื่อได้รับคำสั่งในงานส่งต่อนั้น

## 4. ลำดับงาน

### ขั้น A — ตรวจฐานและล็อกประสบการณ์ที่จะพิสูจน์

อ่านระบบปัจจุบันโดยเน้น GameDefinition, GameState, CompanionScenarioData, CompanionConversation, CompanionDialogueCommands, NpcReplyPolicy, IAiDialogueProvider, ActionCommand, ConditionRule รวมถึงตัวอย่าง Observatory และ tests ที่เกี่ยวข้อง ค้นตำแหน่งจริงจาก develop ล่าสุด

จัดตารางสั้น ๆ: ความสามารถที่มีแล้ว / ช่องว่างที่ขวางเดโม / ข้อมูลเฉพาะ Room01 ที่อยู่ใน core / จุดเชื่อมที่จำเป็น โดยไม่เปิดรอบเก็บข้อจุกจิกทั้งโครงการ

ทำ baseline test และบันทึกฉากการเล่นเดิมหนึ่งรอบ ตรวจปัญหาหลัก: หยุด/ตาม/ยกเลิก, ค้นหา, ช่วยโต๊ะหรือกล่อง, ไม่เปิดเฉลย, เดินไม่ติด, ออกจากบทสนทนาได้ ทบทวนรายงาน PR เดิมเป็นกรณีทดสอบ ไม่ถือว่าทุกข้อยังเกิดในโค้ดล่าสุด

เกณฑ์จบ: รู้ว่าจะใช้ของเดิมส่วนใด และเขียน acceptance scenarios ของขั้น B ได้โดยระบุ state ก่อน/หลังกับผลที่ผู้เล่นเห็น

### ขั้น B — ทำ Room01 ให้มีการร่วมคิดที่เห็นผล

ใช้ NPC หนึ่งตัวและปริศนาหลักหนึ่งชุดก่อน ออกแบบให้หลักฐานของผู้เล่นและ NPC เสริมกัน เปลี่ยนจุดที่กระดาษบอกเฉลยตรง ๆ เป็นข้อมูลสำหรับตีความ โดยยังคงความยากต่ำ

ตัวอย่าง flow สำหรับปรับใช้กับ assets จริง:

1. ผู้เล่นพบสัญลักษณ์หรือข้อมูลส่วนหนึ่ง แต่ยังไม่รู้ลำดับที่ถูกต้อง
2. NPC สังเกตข้อมูลอีกส่วนจากกิจกรรมที่ทำจริง เช่น ช่วยประคองโต๊ะให้ผู้เล่นสำรวจ
3. ผู้เล่นถามว่า “เธอเจออะไรบ้าง” แล้ว NPC รายงานเฉพาะสิ่งที่ตัวเองรับรู้
4. ผู้เล่นเสนอสมมติฐาน เช่น “เราคิดว่าต้องอ่านจากขวา เธอว่าไง” NPC ชี้หลักฐานที่สนับสนุน/ขัดแย้ง หรือยอมรับว่ายังไม่พอ
5. ผู้เล่นตัดสินใจทดลองและเป็นผู้แก้ปริศนา NPC ตอบสนองต่อผลจริง
6. ภายหลัง NPC อ้างถึงความช่วยเหลือครั้งนั้นได้อย่างถูกต้อง

ก่อนแก้เนื้อหา ให้ระบุ fact IDs, แหล่งข้อมูล, ผู้ที่รับรู้, เงื่อนไขเผยแพร่ และคำตอบที่ป้องกันไว้ ใช้ระบบ knowledge เดิมถ้าทำได้ สมมติฐานเป็นคนละสถานะกับข้อเท็จจริง ห้ามบันทึกข้อความคาดเดาของ AI เป็น fact

เตรียมทางเล่นคนเดียวที่ช้าหรือใช้การสังเกตมากกว่า แต่ไม่ติดเพราะความสัมพันธ์ต่ำ อย่าให้กิจกรรมร่วมมือเป็นเพียงรอ animation; ผลต้องช่วยให้ผู้เล่นพบหรือเชื่อมข้อมูล

เริ่มด้วยสมมติฐานที่ออกแบบไว้ไม่กี่แบบและคำถามขอข้อมูลเพิ่มเมื่อไม่เข้าใจ ไม่สัญญาว่าจะเข้าใจเหตุผลภาษาอิสระทุกแบบ

เกณฑ์จบ:

- ผู้เล่นถามข้อมูล เสนอสมมติฐาน ขอคำชี้ทางได้ผ่านข้อความ
- NPC เคลื่อนไหว/ทำงานจริง และให้ผลหลังสำเร็จเท่านั้น
- NPC ไม่รู้สิ่งที่ยังไม่ได้พบหรือได้รับการแบ่งปัน
- คำตอบผิดหรือข้อมูลไม่พอได้รับคำตอบที่มีเหตุผล ไม่แสร้งยืนยัน
- เล่นจบได้ทั้งทางร่วมมือและทางเดี่ยวโดยไม่แก้ state ผ่าน editor

### ขั้น C — ทำให้ความสัมพันธ์และความทรงจำมีผล

กำหนดตารางพฤติกรรมในข้อมูล ไม่ฝังคะแนนกระจัดกระจายในคำสั่ง:

| ระดับความไว้ใจ | พฤติกรรมที่ตั้งใจให้เห็น |
| --- | --- |
| ต่ำ | ให้ข้อสังเกตที่รู้จริง ถามกลับ และช่วยงานพื้นฐาน |
| กลาง | เชื่อมหลักฐานที่อนุญาตและเสนอการทดลองร่วมกัน |
| สูง | อธิบายเหตุผลละเอียดขึ้นและสมัครใจเสนอความช่วยเหลือในจังหวะเหมาะสม |

ทุกระดับยังอยู่ภายใต้ knowledge และ hint permissions เดิม ความไว้ใจสูงไม่ทำให้ NPC รู้ข้อมูลใหม่โดยอัตโนมัติ

เพิ่มความไว้ใจจากเหตุการณ์ที่มีความหมาย เช่น แบ่งปันหลักฐานหรือทำสิ่งที่ตกลงสำเร็จ ใช้ event identity/เงื่อนไขป้องกันการรับคะแนนซ้ำ ไม่ให้ปั๊มจากคำชมซ้ำ ๆ

ความทรงจำเก็บเหตุการณ์ที่ตรวจสอบได้และใช้เลือกบทพูดหรือข้อเสนอภายหลัง ไม่เก็บทุกข้อความอย่างไม่มีขอบเขต กำหนดนโยบายอายุ/จำนวนข้อมูลและ save compatibility

เกณฑ์จบ: state เดียวกันแต่ความสัมพันธ์ต่างกันให้ความช่วยเหลือต่างระดับโดยไม่หลุดเฉลย; ทำเหตุการณ์เดิมซ้ำไม่ได้รางวัลซ้ำ; โหลดเซฟแล้วยังจำเหตุการณ์ถูกต้อง

### ขั้น D — แยกส่วนที่จำเป็นเพื่อให้เกมอื่นใช้ต่อ

ทำทีละขอบเขตหลัง flow หลักผ่าน ไม่ย้ายไฟล์ทั้งหมดหรือสร้าง interface ให้ทุก class ในรอบเดียว

| ส่วน | หน้าที่ | สิ่งที่ไม่ควรผูกไว้ |
| --- | --- | --- |
| Core NPC | ความรู้ ความสัมพันธ์ ความทรงจำ การเลือกความช่วยเหลือ วงจรคำขอ AI และการตรวจผล | ชื่อห้อง เฉลย puzzle ชื่อ Alice หรือ UI ของเกมหลัก |
| Game content | ตัวละคร หลักฐาน คำใบ้ กิจกรรม บทสำรอง เงื่อนไขและผล | key จริงหรือค่าติดเครื่องผู้พัฒนา |
| Host adapters | อ่านสถานะเกม ตรวจ/สั่ง action เดิน interaction UI save และ scene lifecycle | การตัดสินว่า AI พูดแล้วถือว่าทำสำเร็จ |

จุดแยกขั้นต่ำที่ควรพิจารณา โดยใช้ abstraction เดิมถ้ามี:

- ช่องอ่าน world state/ความคืบหน้าที่จำเป็น โดยไม่ส่ง singleton ทั้งก้อนให้ AI
- ตัวสั่งและติดตาม action: ตรวจเงื่อนไข → เริ่ม → สำเร็จ/ล้มเหลว/ยกเลิก พร้อม request identity ป้องกันผลเก่า
- ตัวเชื่อมการเดินและปฏิสัมพันธ์ เพื่อเปลี่ยน implementation ได้โดยไม่แก้ตรรกะ NPC
- การกำหนดคำศัพท์และนโยบายความรู้ตามเกม แยกจากกฎพื้นฐานป้องกันข้อมูลรั่ว
- Provider interface พร้อม mock และข้อความสำรองที่ใช้ได้โดยไม่ตั้ง key

ActionCommand/ConditionRule ที่เป็น enum เดิมยังใช้ต่อได้ผ่าน adapter ถ้าต้องรองรับ action ใหม่ให้เพิ่มช่อง extension ที่มี ID และ handler แบบชัดเจน ห้ามให้ AI ส่งชื่อ method หรือโค้ดเพื่อ execute โดยตรง

การเพิ่มเนื้อหาแบบเดิมต้องทำผ่าน assets; การเพิ่มกลไกใหม่อนุญาตให้เขียน adapter/handler โดยอธิบายไว้ในคู่มือ ไม่ต้องอ้างว่าไม่เขียนโค้ดทุกกรณี

เกณฑ์จบ: เปลี่ยน NPC ห้อง และกฎคำใบ้ผ่านข้อมูลได้โดยไม่แก้ core; Room01–03 และ sample เดิมยังผ่าน regression ที่เกี่ยวข้อง; ไม่เกิด override/ข้อมูลข้ามฉากหรือเซฟข้ามเกม

### ขั้น E — พิสูจน์การติดตั้งในเกมอื่น

เลือกช่องทางแจกจ่ายหนึ่งแบบให้ตรวจสอบได้ แนะนำ local Unity package ถ้า dependency audit รองรับ แยก Runtime / Editor / Tests / Samples~ และประกาศ version/dependencies จริง อย่ารีบย้ายเป็น package ก่อนตรวจ references ของ assets และ asmdefs

สร้าง Unity project ใหม่แยกจาก repository นี้ ใช้ Unity version ที่โครงการรองรับ ติดตั้งเฉพาะ package และ dependencies ที่ประกาศ ห้ามอาศัย Assets, Resources, GUID หรือ singleton ของเกมหลักที่ไม่ได้ส่งไปด้วย

ทำ sample ต่างธีม เช่น NPC ในห้องซ่อมที่ช่วยตรวจอุปกรณ์ ผ่านระบบสนทนา ความรู้ ความสัมพันธ์ และกิจกรรมแบบที่มีอยู่ ใช้ simulated provider ให้เปิดเล่นได้ทันที

เกณฑ์จบ:

- Import/compile และเปิด sample ได้จาก project ใหม่
- สร้าง NPC ใหม่หนึ่งตัวและกิจกรรมชนิดเดิมหนึ่งอย่างด้วย Inspector โดยไม่แก้ source core
- เพิ่ม action ชนิดใหม่ขนาดเล็กผ่าน host extension เพื่อพิสูจน์จุดต่อ โดยไม่แก้ enum/switch ของ core
- Sample ไม่ต้องมี Room01, Alice, เฉลยเดิม หรือ API key จริง
- เพื่อนทำตาม quickstart ได้ บันทึกเวลาที่ใช้และจุดติดจริง ไม่ตั้งตัวเลขความง่ายขึ้นเอง

## 5. แผนทดสอบและหลักฐาน

ทดสอบตามพฤติกรรมสำคัญ ไม่เขียน tests ที่แค่คัดลอก implementation:

- Knowledge/hints: NPC-unknown facts, trust ต่ำ/สูง, คำถามหลอกให้เฉลย, wrapper ไม่ผ่านแล้ว fallback ถูกต้อง
- Conversation/actions: คำขอจริง vs เล่าเรื่อง/ปฏิเสธ/ยกเลิก/เป้าหมายกำกวม; คำขอใหม่หลังยกเลิก; ตอบกลับล่าช้าไม่ทำ action เก่า
- Cooperation: เดินถึงเป้าหมายก่อนช่วย, สำเร็จเมื่อ interaction จริง, รับรางวัลครั้งเดียว, player/NPC ถูกขวางแล้วไม่ค้าง
- Lifecycle: ปิดบทสนทนา เปลี่ยนฉาก โหลดเซฟ ออกจาก sample และ provider ล้มเหลว
- Portability: fresh-project compile/play และ adapter extension ไม่มี dependency ซ่อน

ใช้ EditMode สำหรับนโยบาย/ข้อมูล และ PlayMode สำหรับฉาก การเคลื่อนไหว การยกเลิก และ lifecycle พร้อม mock provider ผล mock ไม่ใช่หลักฐานว่าโมเดลจริงจะตีความภาษาได้ดี

ทำ manual playtest กับคนที่ยังไม่เคยเล่น เป้าหมายเริ่มต้น 3–5 คน เป็นการสำรวจปัญหา ไม่อ้างนัยสำคัญทางสถิติ ให้ลองโดยไม่บอกก่อนว่า NPC คือจุดขาย แล้วถาม/สังเกต:

- ผู้เล่นเป็นฝ่ายกลับไปปรึกษา NPC เองหรือไม่
- บอกได้หรือไม่ว่า NPC ช่วยอะไรในการตัดสินใจ
- มีจังหวะใดรู้สึกว่าคุยกับเพื่อน และจังหวะใดรู้สึกว่า NPC ตอบไม่เกี่ยวข้อง
- ผู้เล่นยังรู้สึกว่าตนเป็นคนแก้ปริศนาหรือ NPC บอกคำตอบหมด
- เวลาที่ใช้ อาการติดขัด การขอความช่วยเหลือ และคำตอบที่โดน fallback จริง

เก็บผลรวมที่จำเป็น ไม่บันทึก key หรือบทสนทนาส่วนตัวโดยไม่จำเป็น หากเกิดปัญหาให้ปรับ flow ที่ทำให้ความร่วมมือไม่เกิดก่อนเพิ่มฟีเจอร์ใหม่

## 6. แบ่งงานให้ตรวจรับได้

1. ชุด A: baseline + acceptance scenarios + ข้อเสนอเนื้อหา Room01 พร้อมข้อมูลที่ต้องเปลี่ยน
2. ชุด B: Room01 ร่วมคิด/ร่วมลงมือครบหนึ่งเส้นทาง พร้อม tests และ fallback
3. ชุด C: trust/memory ที่มีผลจริงและกันรางวัลซ้ำ
4. ชุด D: แยก boundaries เท่าที่ใช้จริง พร้อม regression ของเกมเดิม
5. ชุด E: packaging + fresh-project sample + quickstart + ผล playtest

แต่ละชุดต้องอธิบายปัญหา พฤติกรรมหลังแก้ สิ่งที่ทดสอบ ข้อจำกัด และวิธีลองเล่น หลีกเลี่ยง PR เดียวที่เปลี่ยนเนื้อหาและโครงสร้างทุกส่วนพร้อมกัน หากยังไม่ได้รับคำสั่งเปิด PR ให้เตรียมคำอธิบายส่งต่อในเครื่องไว้ก่อน

เมื่อจบแต่ละชุด อัปเดต checklist ในเอกสารผลดำเนินงานแยกจากแผนนี้ พร้อม SHA และที่อยู่หลักฐาน ไม่ติดป้ายว่าผ่านจากความตั้งใจหรือจากผลทดสอบรุ่นก่อน

## 7. สิ่งที่ยังไม่ต้องขยายในรอบนี้

ยังไม่เพิ่มหลายห้อง หลาย NPC พร้อมกัน ระบบเศรษฐกิจ/combat/farming ความทรงจำไม่จำกัด หรือความเข้ากันได้ทุก engine งานกราฟิกทำเท่าที่ช่วยอ่านการกระทำและสถานะร่วมมือได้ชัด

จุดตรวจรับสุดท้ายคือผู้เล่นเห็นคุณค่าของการมีเพื่อนร่วมแก้ปริศนา และนักพัฒนาอีกคนสร้างตัวอย่างต่างธีมได้จากของที่แจกจริง ทั้งสองอย่างต้องมีหลักฐานแยกกัน

## 8. Prompt สำหรับส่งให้ Sol

อ่าน docs/SOL_NPC_FRAMEWORK_PLAN_TH.md และข้อกำหนดใน repository แล้วลงมือทำตามลำดับ เริ่มจากตรวจ develop ล่าสุดและสร้าง branch ที่ไม่กระทบงานค้าง ใช้แผนนี้เป็นขอบเขตสำหรับสร้าง NPC คู่คิด/คู่ร่วมมือใน Room01 และแยก framework ที่นำไปใช้ใน Unity 2D เกมอื่นได้

เริ่มทำขั้น A และ B ให้เป็นผลลัพธ์ที่ลองเล่นและตรวจรับได้ก่อน แล้วต่อยอด C–E ตาม dependency อย่าหยุดที่การเสนอแผนซ้ำ อย่าขยายไปแก้ข้อจุกจิกหรือสร้าง abstraction ที่ยังไม่ใช้ ตรวจระบบเดิมและรักษา GameState เป็นผู้ตัดสินผลจริง ใช้ AI จำลอง ไม่ใช้โควตาจริง ผู้เล่นต้องพูด/พิมพ์ขอความช่วยเหลือเอง

ทดสอบในระดับที่ตรงกับการเปลี่ยนแปลง บันทึกหลักฐานและข้อจำกัดทุกชุดงาน หากพบการตัดสินใจสำคัญที่แผนไม่ได้ครอบคลุม ให้ระบุทางเลือกและทำงานส่วนที่ไม่ขึ้นกับคำตอบต่อไป ห้าม push/เปิด PR/merge หรือส่งข้อความให้ทีมจนกว่าจะได้รับคำสั่ง รายงานท้ายงานว่าทำครบขั้นใด สิ่งใดทดสอบจริง และสิ่งใดยังต้องตรวจ ไม่เรียก framework ว่าพร้อมใช้ข้ามเกมจนผ่าน fresh-project test
