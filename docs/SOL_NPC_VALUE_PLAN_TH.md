## 1. เป้าหมายที่จะพิสูจน์

ผู้เล่นอธิบายได้ว่า Alice ช่วยให้เขาสังเกต คิด หรือลงมือได้ดีขึ้น และเลือกกลับไปคุยกับเธอเอง ขณะเดียวกันผู้เล่นยังเป็นผู้ตัดสินใจแก้ปริศนา

เป้าหมาย: ให้คนเปิดเล่น Room01 ได้และทีมรู้ว่าติดตรงไหน

งาน:
1. ใช้เส้นทางเดิมให้ครบ: พบโน้ต → ขอช่วย/ค้น → NPC เห็นลูกศร → แลกหลักฐาน → เสนอสมมติฐาน → ผู้เล่นทดลอง → NPC ตอบรับผล → ถามถึงความทรงจำ
2. ตรวจด้วยการเล่นจริงทั้งเส้นทางร่วมมือและเดี่ยว; ใช้ Assets/Editor/FrameworkTools.cs และ BuildSmokePlayer เป็นจุดเริ่มต้นการทำ build ตรวจ output path/scene list ก่อนเรียก ไม่ทับ build ที่ต้องเก็บ
3. เก็บคลิปหรือภาพการเล่นเมื่อมีเครื่องมือรองรับ ระบุความละเอียดและเส้นทาง; หากควบคุม Unity GUI ไม่ได้ ให้ส่ง build/ขั้นตอนให้คนทดสอบและบันทึกช่องว่างไว้
4. เตรียม event trace แบบ local ที่เปิดเฉพาะโหมดทดสอบ: session/build ID, เวลา, room, event kind, request ID, target/fact ID ที่จำเป็น, result/reason, reply route และระยะเวลารอ
5. เหตุการณ์ที่ต้องวัด: request/clarification/action start-complete-cancel-fail, invitation/report, share, hypothesis, puzzle attempt, fallback/rejection และ scene end ใช้จุดส่งเหตุการณ์เดิมก่อนเพิ่ม service
6. trace ต้องไม่เปลี่ยน GameState ไม่ส่งออกเครือข่าย ไม่เก็บ key/prompt/context หรือข้อความดิบเป็นค่าเริ่มต้น ตัวอย่างภาษาจากผู้เล่นเก็บเฉพาะที่ยินยอมและตัดข้อมูลส่วนตัว

ผลส่งมอบ: build ที่เปิดได้ (หรือ blocker ที่พิสูจน์แล้ว), วิธีเปิดเดโม, baseline trace, แบบบันทึก playtest และรายการปัญหาที่กระทบเส้นทางหลัก
เกณฑ์จบ: รู้ว่าผู้เล่นทำแต่ละขั้นสำเร็จจากเหตุการณ์จริง ระบุ latency/fallback route ได้ และเล่นจบแบบออฟไลน์ได้
ทดสอบใหม่เฉพาะ trace มีความเสี่ยง เช่น duplicate callback, cancel/restore, ปิด trace แล้วไม่มีผลต่อ gameplay ไม่เพิ่ม tests เพื่อเช็คชื่อ UI อย่างเดียว

### P1 — ให้ผู้เล่นใหม่ลองก่อนเลือกฟีเจอร์เพิ่ม

เตรียมและดำเนินการกับคน 3–5 คนที่ยังไม่เคยเล่น กลุ่มนี้ใช้หาอาการติดขัดและทิศทางผลิตภัณฑ์ ไม่ใช่งานพิสูจน์นัยสำคัญทางสถิติ

- ก่อนเริ่มบอกเพียงเป้าหมายเกมและการควบคุมพื้นฐาน ไม่แจกประโยคที่ต้องพิมพ์และไม่อธิบายจุดขาย NPC
- เส้นทางเป้าหมาย 5–8 นาทีเป็นสมมติฐานของเดโม ไม่ใช่เวลาที่วัดได้แล้ว หากเกินเวลายังเก็บผลได้
- จดเวลาที่ผู้เล่นเห็น/ตอบสัญญาณ, การขอช่วย, การถามกลับซ้ำ, การยกเลิก, การลองปริศนา และการแทรกแซงจากผู้ทดสอบ
- ถ้าผู้ดูแลต้องบอกคำสั่งตรง ๆ ให้บันทึกว่าได้รับความช่วยเหลือ ไม่นับว่าเข้าถึงระบบเอง
- หลังเล่นถาม: “Alice ช่วยอะไรบ้าง?”, “ตอนไหนรู้สึกว่าทำด้วยกัน?”, “ตอนไหนคุยไม่รู้เรื่อง?”, “ใครเป็นคนคิดและเลือกคำตอบ?”
- บันทึกคะแนน 1–5 เรื่องมีประโยชน์/รู้สึกมีเพื่อน/ตนยังได้ตัดสินใจ พร้อมเหตุผล ไม่สรุปจากคะแนนเพียงอย่างเดียว

เกณฑ์ตัดสินรอบแรกที่เสนอ (เป้าหมายล่วงหน้า ยังไม่ใช่ผล):
- อย่างน้อย 3 จาก 5 คน ยกตัวอย่างประโยชน์ของ Alice ที่เกิดในการเล่นจริงได้ และกลับไปปรึกษาเองอย่างน้อยหนึ่งครั้ง
- ไม่มีเคสที่เล่นต่อไม่ได้เพราะคำสั่ง/บทสนทนา และไม่มีเคสหลุดเฉลยหรือสร้างหลักฐานเอง
- ถ้ามีคนน้อยกว่า 5 ให้รายงานเศษส่วนจริงและใช้เป็นการสำรวจ ไม่ตัดสินผ่านเกณฑ์ 3/5 แทนกัน
- ถ้าคนไม่เห็นประโยชน์ ให้แก้จุดที่ความร่วมมือไม่เกิดก่อน; ถ้าใช้คำไม่ได้ ให้ทำ P2; ถ้าใช้ได้แต่ยังเฉย ๆ ให้ทดลอง P3

ผลส่งมอบ: PLAYTEST_RESULTS_TH.md พร้อมข้อมูลไม่ระบุตัวตน ตัวอย่างคำพูดที่ได้รับอนุญาต 3 ปัญหาหลัก และเหตุผลเลือกงานถัดไป
Sol เตรียมอุปกรณ์/เอกสารและทำ P2 ต่อได้ระหว่างรอคน ห้ามสร้างผล playtest เองหรือวนรัน tests เพื่อแทนขั้นนี้

### P2 — ทำให้การถามกลับจบเป็นการร่วมมือได้

ฟีเจอร์ใหม่ที่ควรทำก่อน: conversational repair หรือจำว่ากำลังถามอะไร ผู้เล่นตอบสั้นตามธรรมชาติแล้วไปต่อได้

ตัวอย่างเป้าหมาย: ผู้เล่น “ช่วยจับให้หน่อย” ในสถานการณ์ที่ยังไม่ทราบเป้าหมาย → Alice ถามว่าจะช่วยอะไร → ผู้เล่น “ขอบโต๊ะ” → เกมตรวจสถานีและเงื่อนไขปัจจุบันแล้วเริ่มช่วย ถ้าประโยคแรกชัดอยู่แล้วให้ใช้เส้นทางเดิม

แนวทาง:
- อ่าน CompanionDialogueCommands, CompanionConversation, DialogueManager และ CanConverse ก่อนเพิ่ม state
- แยกสถานะถามกลับออกจาก active physical task: เก็บ NPC/room/conversation identity, intent ที่มีหลักฐานจากคำขอก่อนหน้า, candidate IDs, สิ่งที่ยังขาด และ turn expiry
- รับเฉพาะคำตอบต่อคำถามที่ระบบเพิ่งถาม เมื่อมี candidate ที่อนุญาตตรงหนึ่งรายการแล้วจึงตรวจผ่าน controller เดิม
- ถ้าคำถามแรกยังไม่ยืนยันว่าจะทำอะไร ห้ามเอาชื่อวัตถุเปล่าไปเดาเป็นคำสั่ง; ถ้าเป็นการเสนอช่วยจาก NPC ต้องมีคำตอบยอมรับชัดเจนจากผู้เล่น
- ข้อความปฏิเสธ/ยกเลิกต้องล้างคำถามค้าง คำขอใหม่ชัดเจนแทนคำขอเดิม บทคุยที่ไม่เกี่ยวข้องให้หมดอายุ ไม่จับค้างจนไปสั่งงานภายหลัง
- ปิดคุย/เปลี่ยน NPC/เปลี่ยนฉาก/reset/load ต้องล้าง context ชั่วคราว ไม่บันทึก clarification ที่ค้างลง save
- ตรวจ live conditions, range และ request revision ซ้ำก่อนลงมือ แม้ provider ตอบช้าหรือ state เปลี่ยน
- คงคำสั่งค้นทั้งห้องตามขอบเขตเดิม ไม่แปลงคำตอบ “ลิ้นชัก” เป็นเริ่มค้นทั้งห้อง และไม่ขยายการจับข้อความหลายช่วงคั่น comma
- เพิ่ม aliases จากตัวอย่างจริงแบบ data-driven ใช้ framework query matcher เดิมเมื่อเกี่ยวข้อง

Acceptance:
1. คำขอขาดเป้าหมาย → ถามกลับ → ระบุเป้าหมายที่ทำได้ → เริ่มงานหนึ่งครั้งและสำเร็จเมื่อทำจริง
2. ไม่มีคำถามค้างแล้วพิมพ์ “ขอบโต๊ะ” อย่างเดียว → ไม่เริ่ม action
3. ตอบปฏิเสธหรือให้สองเป้าหมาย → ไม่เริ่มงาน
4. เป้าหมายใช้ไม่ได้แล้ว → อธิบาย/ถามใหม่ ไม่เดินไปเริ่มตามข้อมูลเก่า
5. เปลี่ยนฉาก/load/close → คำตอบหรือ callback เก่าไม่เริ่มงาน
6. provider ใช้ไม่ได้ → ถามกลับและรับคำตอบต่อเนื่องแบบออฟไลน์ได้

หากต้องเพิ่ม AI classification ให้จำแนกเป็น intent/target ID จากรายการปิด พร้อมข้อมูลที่จำเป็น; engine เดิมเป็นผู้ตรวจสิทธิ์และผล ห้ามใช้ confidence เป็นหลักฐานว่าผู้เล่นยอมรับหรือว่า hypothesis ถูก การขยายภาษาด้วยโมเดลจริงต้องมีชุดข้อความคนจริงและผล provider จริงแยกจาก mock

เกณฑ์จบ: คนสามารถแก้ความเข้าใจคลาดเคลื่อนด้วยการตอบตามบทสนทนา โดยไม่ต้องพิมพ์คำสั่งเต็มใหม่ทุกครั้ง พร้อม regression สำคัญด้าน cancel/state/knowledge

### P3 — ทดลองหนึ่งจังหวะที่ NPC ใส่ใจเป้าหมายร่วมกัน

ทำเมื่อมีหลักฐานว่าเส้นทางหลักใช้ได้แล้วและยังต้องเพิ่มความรู้สึกเป็นคู่ร่วมเล่น เลือกเพียงหนึ่งจังหวะก่อน: หลัง Alice เห็นผู้เล่นลองลิ้นชักไม่สำเร็จ และยังมีข้อมูลที่ทบทวนได้

- ใช้ observation จริงและเงื่อนไขปริศนา ไม่ตรวจข้อความว่า “ฉันทำพลาดแล้ว” เพื่อปลอมว่า NPC เห็น
- ให้เธอส่งสัญญาณชวนทบทวน ผู้เล่นเข้าไปคุยแล้วได้บทตอบที่อ้างถึงสิ่งที่เพิ่งทำ
- ถ้าความรู้ไม่พอ เธอบอกสิ่งที่ขาด; ถ้ามีพอให้เหตุผลภายใต้ระดับคำใบ้เดิม
- แยกข้อความเชิงสังคมกับคำใบ้: ข้อมูลเกินระดับต้องรอคำขอ hint ที่ชัดเจนและผ่านนโยบายเดิม สัญญาณชวนคุยไม่ใช่การอนุญาตให้เฉลย
- trust ต่ำ/กลาง/สูงเปลี่ยนน้ำเสียงและรายละเอียดที่อนุญาต ความไว้ใจไม่สร้าง fact ใหม่และไม่ล็อกเส้นทางเล่นจบ
- ไม่เริ่มค้น/ช่วยเอง ผู้เล่นต้องพิมพ์ยอมรับหรือขอให้ลงมือ
- ใช้ event ID/เงื่อนไข/cooldown เดิม ป้องกันร้องเรียกซ้ำหลังทุกความล้มเหลว เคารพ story event และรายงานที่ยังค้าง
- เมื่อปริศนาสำเร็จหรือเปลี่ยนห้อง ให้ข้อเสนอเก่าหมดอายุ

จุดต่อ: CompanionReflection, Scenario.observations, NpcEventController, CompanionDiscovery และนโยบาย hint ตรวจว่ารวมกับตัวเลือกเดิมได้อย่างไรโดยไม่สร้าง queue ซ้ำอีกชุดโดยไม่มีเหตุผล

เกณฑ์จบ: มีหนึ่งเหตุการณ์ที่ผู้เล่นบอกได้ว่า NPC สังเกตสถานการณ์และช่วยคิดต่อ ไม่ได้รอเพียงคำสั่ง; ทดลองกับคนอีกครั้งและรายงานคำตอบจริง
เก็บตัวอย่างสถานะเดียวกันที่ trust 10/50/80 ด้วย test fixture หรือ demo harness แยกจากเซฟจริง อย่าเพิ่มปุ่ม debug เปลี่ยนคะแนนในเกมปกติ

### P4 — พิสูจน์ความง่ายในการนำไปใช้ต่อ

ทำหลังวงจร Room01 ใช้งานได้และมีผล playtest:
1. ให้ผู้พัฒนาที่ไม่ได้เขียนโมดูลลองติดตั้ง com.mysterygame.companion-reasoning ใน Unity project ใหม่ตาม README

4. เป้าหมาย: sample ทำงานได้โดยไม่มี assets Room01/Alice, เปลี่ยนเนื้อหาโดยไม่แก้ core, เพิ่ม action ผ่าน host extension ได้

ใช้ tools/Test-CompanionPackage.ps1 ตรวจ fresh-project หลังมีการเปลี่ยน package; ผลรันเก่าใช้เป็นประวัติ ไม่อ้างแทน head ใหม่
ผลส่งมอบ: คู่มือที่คนอื่นทำตามได้ พร้อมผลติดตั้งจริง และขอบเขตสิ่งที่นำไปใช้ต่อได้อย่างตรงไปตรงมา

## 5. วิธีใช้ AI และตรวจคุณภาพ

- ชุด mock/offline ตรวจ safety, lifecycle, fallback และ integration ได้ ทำต่อได้โดยไม่ใช้ quota
- ผู้ใช้เคยเลือกไม่ใช้ quota จริง ให้คงข้อจำกัดนี้ เตรียมชุดข้อความสำหรับ real-provider evaluation ไว้ก่อน
- ก่อนเดโมที่อ้างคุณภาพ AI จริง ต้องได้รับอนุญาตใช้ provider แล้ววัด request count, model/provider, latency, fallback/rejection, intent/target accuracy และคำตอบต้องห้ามจากผลจริง ห้ามรายงาน mock เป็นคุณภาพโมเดลจริง
- อย่าส่ง key ลง trace, repository หรือเอกสาร ประเมินเฉพาะชุดข้อความที่อนุญาต
- AI ช่วยตีความภาษาและเรียบเรียงตามบุคลิก; ความจริง/ผล action/สิทธิ์ hint ยังคงตรวจจากเกม
- ไม่ต้องเปลี่ยน provider/model หรือรื้อ framework เพื่อทำ P0–P2

## 6. กติกาการทำงานและการส่งมอบ

- ลงมือทีละชุดที่เล่นและตรวจได้ เริ่ม P0 และ P2 พร้อมเตรียม P1 จากนั้นให้ผลคนเล่นเป็นตัวเลือกการทำ P3/P4
- แก้เฉพาะ blocker ต่อการเล่น/สิทธิ์ข้อมูล/การวัดผลที่พบ หลีกเลี่ยงรอบแก้คำศัพท์จุกจิกที่ไม่มีผู้เล่นพบ
- ใช้ tests เดิมก่อน เพิ่มเฉพาะพฤติกรรมเสี่ยงและกรณีทำซ้ำได้ เลือก EditMode สำหรับ policy และ PlayMode สำหรับ scene/lifecycle
- หากโค้ดไม่เปลี่ยนและ tests ผ่านแล้ว ไม่รันชุดเดิมวนเพื่อเพิ่มตัวเลขหลักฐาน
- เมื่อแตะ Unity runtime หลายระบบ รัน regression ที่เกี่ยวข้องและ suite เต็มก่อนส่งมอบชุดนั้น; งานเอกสารอย่างเดียวตรวจลิงก์/ความถูกต้องก็เพียงพอ
- ไม่เพิ่มหลายห้อง/NPC, planner อิสระ, vector memory, ระบบเศรษฐกิจ หรือ abstraction สำหรับทุกระบบในรอบนี้
- ไม่เปลี่ยนกติกาความสัมพันธ์และเส้นทางเดี่ยวจนผู้เล่นต้องปั๊มคะแนนเพื่อผ่านเกม
- ไม่ push/เปิด PR/merge/ส่งข้อความให้เพื่อนจนได้รับคำสั่งในงานส่งต่อ
- ทุกชุดส่งมอบ: ปัญหาและพฤติกรรมหลังทำ, ไฟล์/commit, วิธีลอง, ผลที่รันจริง, สิ่งที่ยังไม่มีหลักฐาน และงานถัดไป
- บันทึกความคืบหน้าใน SOL_NPC_VALUE_PROGRESS_TH.md แยกจากเอกสารแผน ระบุ P0–P4 เป็น ยังไม่เริ่ม/กำลังทำ/ผ่านอัตโนมัติ/ผ่านคนเล่น/ติดข้อจำกัด ตามหลักฐานจริง

## 7. Prompt ส่งให้ Sol

อ่าน docs/SOL_NPC_VALUE_PLAN_TH.md แล้วทำงานต่อจากสาขา codex/npc-cothinking ซึ่งมี code baseline cebeda8 ตรวจสถานะ/fetch/compare ก่อนและรักษางาน 7 commits หลัง develop a6c6d23 รวมถึงงานเอกสารที่เพิ่มภายหลัง อย่าเริ่มใหม่จาก develop จนงานที่ทำแล้วหาย

เป้าหมายรอบนี้คือให้ผู้เล่นรับรู้คุณค่าของ NPC คู่ร่วมเล่น ทำ P0 ให้มีเดโมและหลักฐานการเล่น เตรียม P1 สำหรับคน 3–5 คน แล้วทำ P2 เรื่องถามกลับและเข้าใจคำตอบสั้นต่อเนื่องโดยยึด live game state พิสูจน์ช่องว่างด้วยกรณีทำซ้ำก่อนแก้ ใช้ระบบ/ข้อมูลเดิมและผู้เล่นพิมพ์คำขอเอง

เริ่มลงมือ ไม่หยุดแค่เสนอแผนซ้ำ ใช้ AI จำลองและไม่ใช้ quota จริง เมื่อยังไม่มีคนทดสอบให้เตรียมสิ่งที่จำเป็นและทำงานอิสระต่อ โดยบอกว่า human evidence ยังรออยู่ ไม่แต่งผลทดสอบ เลือก P3 จากผลเล่นจริง และทำ P4 เมื่อพร้อมพิสูจน์การใช้ต่อ เก็บขั้นตอนและผลใน docs/SOL_NPC_VALUE_PROGRESS_TH.md พร้อม commit และหลักฐาน ไม่ push/PR/merge หรือส่งข้อความให้เพื่อนจนได้รับคำสั่ง
