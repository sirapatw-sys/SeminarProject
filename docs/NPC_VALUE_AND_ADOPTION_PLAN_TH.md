# แผนคุณค่า การนำไปใช้ และการนำเสนอ NPC คู่ร่วมเล่น
วันที่ 16 ตุลาคม 2026 | ตรวจ local HEAD 27c1626 บน codex/npc-cothinking

อัปเดตการทำตามแผน: A แก้และผ่าน regression แล้ว; B มีต้นแบบชวนทบทวนจากการเห็นความล้มเหลว; C/D เตรียมชุดทดลอง และ E มีบทพูด/คู่มือเดโม ดู [สถานะล่าสุด](SOL_NPC_VALUE_PROGRESS_TH.md) และ [รายงานส่งมอบ](VALUE_DELIVERY_20261016_TH.md) ผลตรวจในข้อ 2 ด้านล่างเก็บสภาพก่อนแก้ ไม่ใช่รายการบั๊กค้างปัจจุบัน

เอกสารนี้เป็นแผนถัดไปและข้อสรุปรอบตรวจ แทนลำดับงานใน SOL_NPC_VALUE_PLAN_TH.md ที่อ้าง baseline เก่า อ่านร่วมกับ SOL_NPC_VALUE_PROGRESS_TH.md และ protocol เดิม ไม่ได้แก้ runtime ในรอบนี้ ไม่ได้ fetch หรือรับรองสถานะ remote ล่าสุด

## 1. ข้อเสนอหลัก

สร้าง NPC คู่ร่วมแก้ปัญหาสำหรับเกมปริศนา Unity: รู้จากหลักฐานที่พบจริง ช่วยทำงานจริง ร่วมคิดตามระดับความไว้ใจ และให้ผู้เล่นเป็นคนตัดสินใจ ส่วนผู้พัฒนาออกแบบข้อเท็จจริงและการช่วยเหลือผ่านข้อมูลที่ตรวจสอบได้

กลุ่มแรกที่เหมาะจะทดลองใช้คือทีมเกมอินดี้/นักศึกษาที่ทำเกมปริศนาหรือสืบสวนใน Unity ไม่ขยายคำสัญญาไปถึงเกมทุกประเภท
สิ่งที่ผู้เล่นควรเล่าได้หลังเล่น: “ฉันมีข้อมูลส่วนหนึ่ง เธอเห็นอีกส่วน เราคุยกันและทดลองจนผ่านได้”
สิ่งที่ผู้พัฒนาควรทำได้: สร้างตัวอย่างต่างธีมโดยเปลี่ยนข้อมูล/ต่อ host adapter และไม่แก้ reasoning core

ยังไม่มีหลักฐานว่าดีกว่าเกมอื่นโดยรวม เป้าหมายคือพิสูจน์ประโยชน์เฉพาะด้านและการนำไปใช้จริง

## 3. อะไรควรเป็นความต่าง

การ “คุยได้และทำ action ได้” เพียงอย่างเดียวไม่พอเป็นคำกล่าวว่าใหม่กว่าเครื่องมืออื่น ตัวอย่าง Convai มีเอกสาร action integration อยู่แล้ว:
https://docs.convai.com/api-docs/api-reference/core-api-reference/character-crafting-apis/action-api
ตรวจ 16 ตุลาคม 2026; หน้าเดิมระบุให้ integration ใหม่ใช้ Agentic Actions/SDK ปัจจุบัน ใช้แหล่งนี้เพียงยืนยันว่ามีความสามารถประเภทนี้ ไม่ใช่ผล benchmark คู่แข่ง

| คุณค่าที่เลือกพิสูจน์ | สิ่งที่ต้องโชว์ | สิ่งที่ไม่ควรกล่าวอ้างตอนนี้ |
| --- | --- | --- |
| คู่ร่วมคิดจากหลักฐาน | ก่อนพบข้อมูลบอกว่าไม่รู้ หลังพบ/แลกข้อมูลอ้างเหตุผลได้ | AI คิดแก้ปริศนาอิสระทุกแบบ |
| ความไว้ใจมีผลที่ออกแบบได้ | สถานะหลักฐานเดียวกัน คำช่วย trust ต่ำ/สูงต่างกันโดยไม่หลุดข้อมูล | ความสัมพันธ์ทำให้เกมสนุกขึ้นแล้ว |
| ช่วยลงมือและเคารพผู้เล่น | ขอช่วย → เดิน/จับจริง → ผู้เล่นลงมือ → เกิดผล; สั่งหยุดแล้วหยุด | ข้อความจากโมเดลเท่ากับ action สำเร็จ |
| ใช้ต่อได้โดยควบคุมกติกา | เกมปริศนาและ Repair Workshop ใช้ core เดียวกัน | ติดตั้งแล้วได้ movement/UI/save ของทั้งเกม |

## 4. ลำดับงานสำหรับ Sol

### A — ปิดช่องโหว่สิทธิ์ลงมือ (ทำก่อน)
- ตรวจ worktree/AGENTS และ compare develop ใหม่ก่อน implementation; รักษางานบน branch นี้
- เพิ่มเงื่อนไขยืนยันเจตนาขอช่วยในเส้นทาง proposed action รวมถึง search ที่แปลงเป็น help
- คำตอบชื่อวัตถุใช้ได้เมื่อรับคำถามค้างที่ยังถูกต้องเท่านั้น คง lifecycle/live conditions/cancellation เดิม
- ทำ regression จาก probe ทั้ง 8 combinations พร้อมคำขอจริง เช่น “ไปช่วยตรงโต๊ะหน่อยสิ” และการตอบชื่อหลังถามกลับ
- ผ่าน focused tests และ suite ที่เหมาะกับ runtime ที่เปลี่ยน; ไม่ขยายไปแก้ข้อความหลาย clause
จบเมื่อ: ทั้งคำขอจริงและการถามกลับทำงาน แต่ชื่อสิ่งของเฉย ๆ ไม่สั่งงาน; แก้ข้อความ progress ให้ตรงหลักฐาน

### B — ทำ Room01 เป็นเดโมความร่วมมือที่อ่านออก
- เล่นเส้นทางครบทั้งแบบร่วมมือและเดี่ยว ตรวจการหยุด/ค้น/ช่วยโต๊ะ/กล่อง/ปิดคุยด้วยคน
- ตรวจภาพท่าจับ จุดยืน ทิศหัน และ feedback เริ่ม/จบ/ทำไม่ได้ ให้คนเห็นทันทีว่าใครกำลังทำอะไร ใช้สถานะสั้นเฉพาะช่วงทำงาน ไม่เพิ่มกล่องกลางจอถาวร
- ใช้หลักฐานคนละส่วนที่มีอยู่แล้ว: ผู้เล่นพบโน้ต, NPC พบลูกศร → แลกข้อมูล → ผู้เล่นเสนอวิธี → ทดลองเอง
- ออกแบบหนึ่งจังหวะชวนทบทวนหลัง NPC เห็นความล้มเหลวจริง ใช้ observation/indicator/cooldown เดิม; ผู้เล่นเลือกเข้าไปคุย ไม่บังคับเปิดบทสนทนา
- หากผลเล่นจริงพบว่าไม่ต้องมีจังหวะใหม่ ให้ปรับความชัดเจนของ feedback เดิมก่อน
- ความสัมพันธ์เปลี่ยนสำนวน/รายละเอียดที่อนุญาต ไม่ล็อกการเล่นจบหรือให้ fact ฟรี
จบเมื่อ: ผู้เล่นอ่าน action ออก เดโมจบได้ และมีอย่างน้อยหนึ่งเหตุการณ์อ้างถึงสิ่งที่ทำร่วมกันจริง

### C — วัดคุณค่ากับคนที่ไม่รู้คำสั่ง (ทำคู่กับการปรับ B)
- ใช้ ROOM01_PLAYTEST_PROTOCOL_TH.md กับผู้เล่นใหม่ 3–5 คน เริ่มจาก offline build
- บอกเป้าหมายและวิธีควบคุม ไม่บอกประโยคสั่ง NPC ล่วงหน้า จดทุกครั้งที่ผู้จัดต้องช่วย
- เก็บจำนวนคนที่ขอความช่วยเหลือสำเร็จ กลับมาคุยเอง และยกตัวอย่างประโยชน์ของ NPC ได้ พร้อมความรู้สึกเป็นเพื่อน/agency และตัวอย่างเหตุการณ์
- เป้าหมาย pilot เดิม 3/5 เป็นเกณฑ์ปรับงาน ไม่ใช่ข้อพิสูจน์เชิงสถิติ; รายงานจำนวนจริงเมื่อได้ไม่ครบ 5
- เลือกแก้สามอุปสรรคหลักจากผลจริง; เพิ่ม alias จากข้อความที่ยินยอมให้เก็บ ไม่วนขยาย regex โดยไร้ผู้เล่น
- ถ้าจะเปรียบเทียบ: เตรียม baseline คำใบ้แบบคงที่กับ companion บนปริศนาที่ความยากใกล้กัน สลับลำดับ/ฉากระหว่างคนเพื่อลดจำคำตอบ และบันทึกความต่างของเงื่อนไขทั้งหมด
- อย่าให้คนแก้ห้องเดิมสองรอบแล้วอ้างว่าเวลาที่เร็วขึ้นมาจาก NPC; pilot เล็กใช้หาจุดติดก่อนออกแบบการทดลองขนาดเหมาะสม
จบเมื่อ: มี session จริง ผลทั้งที่ดีและไม่ดี และตัดสินใจแก้จากหลักฐานได้

### D — พิสูจน์ว่าทีมอื่นใช้ได้
- เริ่มจาก package 0.2 และ Repair Workshop ที่มีแล้ว ไม่สร้างระบบแยกซ้ำ
- ให้เพื่อนที่ไม่เขียน core ติดตั้งจากคู่มือใน Unity project ใหม่ แล้วเปลี่ยนเป็นปริศนาต่างธีม 1 แบบ
- ภารกิจ: เพิ่ม facts 2 รายการ, hypothesis 1 รายการ, ระดับช่วย 3 ระดับ, host action 1 อย่าง โดยไม่แก้ core
- วัดเวลาถึง sample แรก/เนื้อหาใหม่ จำนวนครั้งที่ต้องถาม ไฟล์ host ที่ต้องเขียน และปัญหา dependencies; เป้าหมายทดลอง sample ภายใน 30 นาที เนื้อหาใหม่ภายใน 90 นาที ไม่ใช่ผลที่ทำได้แล้ว
- ต่อเติมคู่มือ install → configure → integrate → troubleshoot พร้อมตารางความรับผิดชอบ core/host, version compatibility, offline limitations และ third-party notices
- ถ้า consumer ที่สองต้องใช้ action lifecycle จริง ค่อยสกัด interface จากสองกรณี ไม่แยกทุกระบบล่วงหน้า
- รัน package smoke เมื่อ package เปลี่ยน และให้คนลองตามคู่มือจริงอีกครั้ง
จบเมื่อ: มีโปรเจกต์ตัวอย่างที่ไม่มี Room01/Alice, ผู้พัฒนาอื่นทำสำเร็จ และขอบเขตสิทธิ์เผยแพร่ที่เจ้าของทีมตกลงแล้ว

### E — จัดชุดหลักฐานสำหรับนำเสนอ
- เดโมที่เปิดได้, clip สำรองจาก build เดียวกัน, commit/build ID และวิธี reset ที่ลองแล้ว
- หน้าแนะนำสั้น: ช่วยใคร/ปัญหาอะไร/คลิป 60–90 วินาที/ติดตั้ง/ตัวอย่างสองธีม/ขอบเขตและสถานะ
- แสดงผลคนจริงกับผล automatic แยกกัน มีตัวอย่าง failure และวิธีรับมือหนึ่งกรณี
- หากยังไม่ทดสอบ provider จริง ใช้คำว่า offline prototype/mock integration ให้ตรง และอย่านำเสนอคลิป offline เป็นความสามารถ generative AI สด
- เก็บชุดข้อความสำหรับ provider evaluation ไว้ได้ แต่ยังไม่ใช้ key/quota จริงจนได้รับอนุญาต
จบเมื่อ: คนดูเข้าใจประโยชน์ในหนึ่งนาที และผู้พัฒนารู้ว่าจะเริ่มลองตรงไหน
